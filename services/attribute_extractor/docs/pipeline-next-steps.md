- Папка `data/` и содержимое `models/` — генерируемые артефакты, в репозиторий
  не попадают.
- Тестовый набор зелёный (все модульные и интеграционные тесты проходят).

Ключевые уже готовые сущности, которые НЕ нужно реализовывать заново

- `enums.py`: `ExtractionMethod` (`rule|ner`), `ExtractionStatus`

Точное поведение всех эндпоинтов — в спецификации

## Задача 1. HTTP API сервиса

Ветка: `feat/pipeline-api`. Файлы: `src/attribute_extractor/main.py`
(при желании роуты можно вынести в отдельный модуль рядом; фабрика
`create_app()` должна сохранить поведение). Экземпляр `ExtractPipeline`
создаётся один раз на уровне приложения, запросы не несут состояния.

Реализуются эндпоинты ниже; префикс — `settings.api_prefix` (`/api/v1`).

### 1.1 POST `/api/v1/extract`

- Вход: модель `ProductCardRequest` → ответ: `ExtractionResult` пайплайна
  без изменений (его структура совпадает с `ExtractionResponseItem`
  из спецификации).
- Ошибки: 422 — стандартная валидация FastAPI; 500 — тело в формате
  `ErrorResponse`.
- Важно: запрос с пустым текстом, но непустыми `seller_attributes` проходит
  валидацию контракта; пайплайн вернёт `status=skipped` (вход пайплайна —
  только `title`/`description`), и это должен быть ответ 200.
- Нарушение инварианта очистки текста (пайплайн бросает `ValueError`) —
  ответ 500 с `ErrorResponse` (простая обёртка в обработчике исключений).

### 1.2 POST `/api/v1/extract/batch`

- Вход: `BatchExtractRequest` → ответ: `BatchExtractResponse`.
- Каждая карточка обрабатывается независимо: вокруг вызова пайплайна —
  перехват исключений на каждый элемент; ошибка одной карточки даёт ей
  `status=error` и НЕ прерывает батч (частичный успех обязателен).
- `threshold_override` (float, опциональный) — разовая замена порога
  «автоматическое принятие» на текущий запрос; глобальные настройки не
  мутируются, влияет только на `needs_review`, `low_confidence_count` и
  `status` результатов этого батча. Если у пайплайна нет готового параметра
  для этого — реализовать локальным переопределением соответствующих
  аргументов/компонентов, НЕ переделывая модель `Settings`.
- Сводка `BatchExtractResponse`: `total`, `ok`, `low_confidence`, `errors`
  (счёт по карточкам со `status=error`), `results`,
  `processing_time_ms_total`.
- Лимиты `batch_size` (1–50) уже встроены в валидацию Pydantic — код 422
  получается автоматически.

### 1.3 GET `/api/v1/categories`

- Параметры: `category` (необязательный фильтр), `limit` (по умолчанию 50,
  максимум 200), `offset` (по умолчанию 0).
- Ответ: `{"items": [CategorySchema], "total": N}`.
- Честность данных: зарегистрированных схем категорий пока нет, отдаётся
  дженерик-схема. Придумывать фейковые схемы нельзя.

### 1.4 GET `/api/v1/categories/{category}`

Схема категории; 404 → `ErrorResponse`, если в реестре не найдена.

### 1.5 GET `/api/v1/health`

Расширить текущий тривиальный эндпоинт до модели `HealthResponse`:
- `status=degraded`, если правила работают, но NER-модель/индекс не загружены
  (на сегодня это штатный режим: `models_loaded: ["rules", "vector_index"]`);
- `version` — версия сервиса, `pipeline_version` — версия пайплайна,
  `uptime_seconds` — время с момента старта приложения.

### 1.6 GET `/api/v1/info` и GET `/api/v1/config`

- `info` — по спецификации: имя/версия сервиса, версии пайплайна,
  `extraction_methods: ["rule", "ner"]`, `default_threshold`,
  `supports_batch: true`, `max_batch_size`, признак `text_only: true`,
  блок `features` (флаги: grounding_required, normalization, unit_conversion;
  `traffic_weighted_metrics: false` — отложено).
- `config` — read-only: пороги уверенности (`confidence_thresholds` — auto
  и review), `match_threshold`, `deterministic_confidence`; без секретов.

### Также в задаче 1

## Задача 2. Офлайн-прогон и выгрузка предсказаний — `scripts/run_batch.py`

Ветка: `feat/pipeline-batch`.

### 2.1 Файл и режим

Скрипт в стиле существующего `scripts/build_field_catalog.py`: тяжёлые
импорты — внутри функций, чтобы не нагружать зависимостями обычные
CLI-вызовы скриптов.

Режим по умолчанию: офлайн, без HTTP — напрямую используется экземпляр
`ExtractPipeline`. Опция `--api <base_url>` — вызовы HTTP-эндпоинта батча
(имеет смысл после выполнения задачи 1). Первая реализация — офлайн-режим.

### 2.2 Вход

Файлы `.csv` / `.json` / `.tsv`, колонки/поля: `product_id`, `title`,
`description`, `seller_attributes` (строка JSON — разобрать; невалидный
JSON → карточка с `status=error`, поток не прерывается), `category_id`,
`category_name`. Проверки входа: файл непустой, разумного размера,
расширение распознано (по аналогии с bulk-загрузкой из спецификации
фронтенда).

### 2.3 Обработка

- Поток обрабатывается частями по `--batch-size` (по умолчанию 20,
  максимум 50).
- Для каждой карточки вызов `ExtractPipeline.extract`; настройки — из
  переменных окружения; CLI-опции только `--batch-size` и `--max-items`
  (урезать вход для быстрой пробы).
- Отказоустойчивость: одна битая карточка не приводит к потере остальных.

### 2.4 Выход (два артефакта)

1. `predictions.jsonl` — по одной строке на карточку, сериализованный
   `ExtractionResult` (вход для задачи 3).
2. По флагу `--csv`: таблица формата `PredictionRow` — колонки
   `product_id`, `title`, `category`, `needs_review`, `status` и для каждого
   атрибута пара `[attribute_code]` = `normalized_value`,
   `[attribute_code]_confidence` = `confidence` (формат экспорта
   предсказаний со страницы фронтенда).

### Тесты задачи 2

`tests/test_attribute_extractor_run_batch.py`:
- маленький CSV во временном каталоге (три строки; в одной — битый JSON
  в `seller_attributes` → `error`, остальные корректны);
- проверка: `predictions.jsonl` содержит валидные `ExtractionResult`,
  состав колонок CSV соответствует формату;
- запись строго во временный каталог, не в репозиторий.

### Критерий приёмки задачи 2

- Прогон на `gold/gold.jsonl` (100 карточек) → `predictions.jsonl` со
  100 результатами и без traceback — первичный материал для задачи 3.
- README: короткий пример вызова в разделе «Запуск».

## Задача 3. Метрики на gold — `scripts/evaluate.py` и первый отчёт

Ветка: `feat/pipeline-evaluate`. Спецификация метрик: `attribute_extractor.md`,
раздел 8 (столбец «Способ расчёта» — формулы; взвешивание по трафику
отложено сознательно и в этой задаче не реализуется).

### 3.1 Вход

- `gold/gold.jsonl` — эталон: 100 карточек (`card`: `sku_id`, `title`,
  `description`, `category_*`; `expected`: `{attribute_code,
  normalized_value}`; пояснения — в `notes`).
- `predictions.jsonl` из задачи 2; если его нет — прогнать пайплайн прямо
  в скрипте по gold-карточкам (тот же `ExtractPipeline`).
- Сопоставление карточек gold ↔ предсказаний: по идентификатору
  (`product_id` из карточки = `sku_id` из gold; в predictions.jsonl это
  поле уже заполнено).

### 3.2 Сопоставление и метрики

- Сопоставление по паре `(product_id, attribute_code)`; сравнение
  **exact-match** по `normalized_value`; при `allow_multiple` — пересечение
  множеств (таких атрибутов сейчас нет, но формулу заложить).
- Счётные величины (по каждому атрибуту + макро + микро):
  Precision = TP/(TP+FP), Recall = TP/(TP+FN), F1 = 2·P·R/(P+R).
- Coverage по каждому атрибуту (доля карточек с предсказанием).
- Разрез по категориям (`category_name` из gold).
- Доля предсказаний ниже порога (`confidence < AUTO_THRESHOLD`) — оценка
  нагрузки ручной проверки.
- Доля предсказаний, отброшенных grounding, — оценка жёсткости фильтра.
  Способ без изменений пайплайна: взять кандидатов после слияния,
  прогнать `GroundingValidator.filter` отдельно и сравнить объёмы
  (до/после).
- SoftMatch — не делать в этой задаче.
- Важный момент трактовки: пороги влияют только на статусы и
  `needs_review`, но не на состав предсказаний. Это отразить в отчёте.

### 3.3 Пороги и ablation

- Простая сетка порога «автоматическое принятие» [0.7, 0.8, 0.9] — только
  как отчёт о доле карточек, уходящих на ручную проверку; решение о
  финальном значении — отдельное управленческое решение.
- Переключение путей — через переменные окружения тумблеров пайплайна
  (`enable_rules`, `enable_ner`, `enable_vector_match`). NER пока не
  обучен, поэтому ablation «rules vs rules+NER» появится позже, в задаче
  NER.
- Взвешивание по трафику — отложено сознательно.

### 3.4 Выход

- Человекочитаемая таблица в stdout (без новых зависимостей).
- Флаг `--out metrics.json`: агрегированные метрики по атрибутам и
  категориям.

### Тесты задачи 3

`tests/test_attribute_extractor_evaluate.py` на синтетических данных во
временном каталоге (без внешних сервисов):
- контрольные значения: TP=1, FP=1, FN=1 → P=R=F1=0.5;
- coverage; разрез по категориям; доля ниже порога — ожидаемые значения.

### Критерий приёмки задачи 3

- Полный прогон: таблица P/R/F1 по 9 атрибутам на 100 gold-карточках для
  rule-пути, размещённая в описании финального PR этого блока (первый
  количественный отчёт проекта).
- В выводе отдельно указать, какие атрибуты сильные/слабые и почему
  (примеры сверять с `notes` gold).

## Общие конвенции и ограничения (для всех задач)

1. **Спецификации** (`openspec/specs/`) — источник истины; менять без
   явного согласования запрещено.
2. **Структура работ**: одна задача — одна ветка и один PR; в описании PR —
   что сделано и как проверялось. Тесты обязательны; удалять или ослаблять
   существующие тесты нельзя.
3. **Коммиты**: не затрагивать сгенерированные каталоги (`data/`,
   `models/`, `EDA/scripts/`); локальные файлы предсказаний в PR не
   попадают.
4. **Стиль**: новые абстракции — только при необходимости; использовать уже
   существующие компоненты; комментарии в коде — по делу; README и другие
   пользовательские тексты — на русском.
5. **Совместимость**: не ломать существующие подписи (`ExtractPipeline.extract`,
   модели контрактов); публичные API сохраняют обратную совместимость.
6. **Магические числа**: новые лимиты и значения по умолчанию — в
   `constants.py`, не в бизнес-логике; CLI-флаги упрощают прогон, но не
   отменяют константы по умолчанию.
7. Каждая задача завершается полным зелёным тестовым набором и чистым
   линтером перед открытием PR.
