# EDA — разведочный анализ данных SpecFlow

Разведочный анализ датасета кейса М.Видео: извлечение характеристик товаров
из текстовых карточек. Анализ распознаёт поля, пропуски, распределения, связи
между источниками и аномалии, строит графики и собирает итоговый PDF-отчёт.

## Что внутри

```
EDA/
├── dataset/                 # исходные данные (не коммитятся, ~2.4 ГБ)
│   ├── sku_desc.parquet     # 1 177 200 текстовых карточек
│   ├── skus.pkl             # YML-каталог: 546 069 офферов с атрибутами
│   └── query_clicks.parquet # 30 991 350 строк кликового трафика
├── src/                     # воспроизводимый код анализа
│   ├── config.py            # пути, целевые категории и атрибуты
│   ├── loaders.py           # загрузка источников и кэширование
│   ├── cards.py             # анализ текстовых карточек
│   ├── catalog.py           # анализ каталога и атрибутов
│   ├── traffic.py           # анализ трафика
│   ├── coverage.py          # связи источников и заземление атрибутов
│   ├── plotting.py          # построение графиков
│   ├── report.py            # сборка PDF-отчёта (reportlab)
│   └── run.py               # оркестратор
├── figures/                 # 21 сгенерированный график (PNG)
├── results/                 # таблицы-выгрузки (CSV)
├── cache/                   # промежуточные агрегаты (не коммитятся)
├── EDA_report.pdf           # итоговый PDF-отчёт
└── requirements.txt         # зависимости анализа
```

## Как запустить

Зависимости анализа не входят в корневой workspace сервисов и не ставятся
через `uv sync`. Есть два способа. Команды выполняются из корня репозитория.

### Вариант 1. Через nix-shell (как в текущем окружении)

```bash
nix-shell -p 'python3.withPackages (ps: with ps; [ pandas pyarrow matplotlib seaborn reportlab ])' \
  --run "PYTHONPATH=EDA python3 -m src.run --stage all"
```

### Вариант 2. Через virtualenv

```bash
python3 -m venv EDA/.venv
EDA/.venv/bin/pip install -r EDA/requirements.txt
PYTHONPATH=EDA EDA/.venv/bin/python -m src.run --stage all
```

Отдельные стадии:

```bash
... python3 -m src.run --stage analysis   # только расчёты
... python3 -m src.run --stage figures    # только графики
... python3 -m src.run --stage report     # только PDF
... python3 -m src.run --stage analysis --force  # пересчитать аналитику
```

Расчёты кэшируются в `cache/`: повторный запуск пропускает уже посчитанные
стадии. Полный первый прогон занимает несколько минут (распаковка `skus.pkl`).

## Ключевые выводы

- **Три несогласованных среза.** Пересечение по SKU низкое: карточки и каталог
  совпадают лишь по **241 355** SKU, во всех трёх источниках сразу — **102 945**.
  Обучаться и валидироваться можно только на пересечении.
- **Эталон лежит в структуре, а не в тексте.** Атрибуты есть у офферов каталога
  (в среднем **38,4** параметра на товар, **10 708** уникальных имён после
  слияния дублей `_search`). Текст карточки — неструктурированный вход.
- **Длинный хвост.** 5 486 имён атрибутов встречаются реже 100 раз, 1 517 — реже
  пяти. Единый ручной словарь невозможен; нужна каскадная схема.
- **Заземление атрибутов.** Бренд находится в заголовке в **98,2%** случаев,
  модель — в **95,9%**, а цвет — лишь в **16,8%**. Цвет нельзя брать из текста
  без словаря и структурного поля.
- **Грязный текст.** **49,3%** описаний содержат HTML-теги, **44,4%** — `<br>`;
  **41,1%** заголовков — дубликаты (шаблонные «пустые» карточки).
- **Структура каталога чистая.** Единицы в `@unit` стандартизованы, словари
  значений узкие (память — 19 уникальных, цвет — 1 675 с дублями по регистру и «ё»).
- **Служебный шум.** Часть «атрибутов» каталога — не товарные характеристики:
  `Подборки`, `Продавец`, `Потратить бонусы`, `Гарантия предоставляется`, BI-поля.

Подробный разбор с графиками — в `EDA_report.pdf`.
