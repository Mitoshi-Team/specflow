# Frontend

Веб-приложение SpecFlow на React, TypeScript и Vite. Тексты интерфейса
локализованы через i18next.

## Устройство

- `src/main.tsx` — точка входа (включая `BrowserRouter`).
- `src/App.tsx` — корневой компонент с маршрутами.
- `src/components/` — переиспользуемые компоненты (`AppLayout`, `Header`,
  `InputModeSwitch`, `FileUpload`, `CardTextInput`, `DataPreview`,
  `BatchControls`, `ErrorBanner`, `ResultsSummary`, `StatusLegend`,
  `ResultsTable`, `ExportCsvButton`).
- `src/pages/` — страницы (`PageHome`, `PageResults`).
- `src/hooks/` — кастомные хуки (`useFileParser`, `useBatchExtract`,
  `useCsvExport`).
- `src/lib/` — утилиты (`fileParser` — разбор CSV/JSON/TSV, `inputValidation` —
  валидация обязательных полей, `format` — форматирование значений,
  `lastBatch` — сохранение последнего батча между переходами).
- `src/styles/tokens.css` — токены дизайн-системы (цвета, типографика,
  геометрия).
- `src/index.css` — глобальные стили оболочки и состояний компонентов.
- `src/constants.ts` — константы уровня приложения (в т.ч. параметры
  загрузки файлов).
- `src/i18n.ts` — конфигурация i18next.
- `src/locales/` — переводы (`ru`, `en`).
- `src/schemas/api.ts` — TS-типы, синхронизированные с API-контрактом
  (`openspec/specs/api_contract.md`).
- `src/api/` — клиент API на fetch: единая точка отправки запросов
  (`client.ts`), типизированные методы по эндпоинтам (`index.ts`).
- `public/specflow_logo.svg` — логотип SPECflow (прозрачный фон,
  используется в шапке как есть).
- `vite.config.ts` — конфигурация Vite и dev-сервера.

## Дизайн

Визуальный язык задан дизайн-системой `openspec/specs/design.md`:

- цвета, типографика, радиусы и отступы вынесены в `src/styles/tokens.css`;
  компоненты используют только CSS-переменные;
- палитра монохромная: оттенки серого плюс красный только для ошибок и
  критичных состояний (синий и другие декоративные акценты не используются);
- реализована тёмная тема (основная по спеке); светлая тема и переключатель
  из дизайн-спека пока не подключены;
- в шапке — логотип и название текущего раздела; служебные индикаторы
  (версия пайплайна, статус API) в шапке не показываются;
- фон рабочей области — слабая CSS-сетка, без растровых изображений;
- переходы короткие (`--transition-fast`), при
  `prefers-reduced-motion: reduce` отключаются;
- фокус заметен везде (`:focus-visible`), статусы дублируются текстом.

## Маршруты

- `/` — `PageHome` (главная).
- `/results` — `PageResults` (результаты батча).

Страницы рендерятся внутри `AppLayout` (Header + область контента).
`Header` показывает логотип и название текущего раздела; навигация ведёт на
страницы «Главная» и «Результаты».

## Загрузка карточек

Карточки можно подать двумя способами; переключатель `InputModeSwitch`
(сегментный контрол из radio-кнопок) находится в заголовке панели загрузки:

- **Файл** — текущий способ по умолчанию: CSV/JSON/TSV со списком карточек.
- **Текст карточки** — описание одной карточки в текстовом поле.

- `InputModeSwitch` — выбор способа загрузки (`file` / `text`); в режиме
  `text` событие выбора файла недостижимо, в режиме `file` — наоборот.
- `FileUpload` — выбор файла (CSV/JSON/TSV) обычным системным диалогом по
  клику; перетаскивание не поддерживается. Отображает состояния ожидания,
  обработки, ошибки и успеха. Компонент не разбирает файл: он принимает статус
  и ошибки снаружи.
- `CardTextInput` — текстовое поле для описания одной карточки; непустой
  после обрезки пробелов текст становится карточкой с полем `description`
  (больше полей в этом режиме не задаётся). Валидацию компонент не
  выполняет — она выводится из состояния текста: пусто — ожидание,
  непусто — карточка готова к обработке. Поле растёт по числу строк
  (`CARD_TEXT_MIN_HEIGHT_PX`…`CARD_TEXT_MAX_HEIGHT_PX` из `src/constants.ts`),
  выше максимума включается внутренний скролл; ручное растягивание за угол
  отключено.
- `useFileParser` — разбор выбранного файла: определение формата по расширению,
  чтение, парсинг и валидация минимального набора полей. Возвращает карточки
  (`ProductCardRequest[]`) либо типизированную ошибку (`FileParseError`).
- `lib/fileParser.ts` — чистые функции разбора (без React), покрытые тестами.
- `DataPreview` — предпросмотр первых `PREVIEW_MAX_ROWS` строк: сводка
  валидации обязательных полей (`title`, `description`, `seller_attributes`),
  ключевые поля, обрезка длинных значений с раскрытием, отметка
  незаполненных ячеек; метаданные файла (имя, формат, размер, число
  карточек) показывает `PageHome`.

`PageHome` связывает способы загрузки и предпросмотр: выбор файла запускает
разбор, кнопка «Убрать файл» сбрасывает состояние; в текстовом режиме
предпросмотр строится из одного введённого описания, кнопка «Очистить текст»
возвращает его в исходное состояние. Переключение режима не теряет данные
другого режима. Успешный ввод сам по себе обработку не запускает.

Формат определяется по расширению; CSV/TSV разбираются через `papaparse`.
Валидация строки: минимум одно непустое из `title`, `description`,
`seller_attributes`; `seller_attributes` в CSV/TSV должен быть корректным JSON.
Разобранные карточки совпадают с типом `ProductCardRequest`
(`src/schemas/api.ts`).

## Обработка батча и результаты

- `BatchControls` — размер батча и порог уверенности, кнопки «Обработать»,
  «Сброс» и «Новый батч», прогресс «Обработано X из Y». Запуск, прогресс и
  ошибки приходят снаружи через `useBatchExtract`. Оба числовых поля
  проверяются на диапазон (размер — целое 1–50, порог — 0–1): при
  недопустимом значении под полем показывается ошибка диапазона, а кнопка
  «Обработать» блокируется. Пустое поле считается недопустимым, а не нулём.
- `ErrorBanner` — понятное сообщение ошибки, безопасное следующее действие
  подбирается по статусу/коду ответа (`apiErrorHintKey`) и разворачиваемые
  технические детали (HTTP-статус, `detail`, ошибки валидации).
- `FileUpload` при ошибке разбора показывает не только причину, но и
  подсказку «что исправить» (`fileUpload.hints.<code>`).
- При успехе батча `PageHome` сохраняет ответ, порог и исходные карточки в
  localStorage (`lib/lastBatch`) и переходит на `/results`. Хранение в
  `location.state` не подходит: при повторном переходе из навигации и при
  перезагрузке состояние маршрута теряется, и результаты пропадают.
- `PageResults` читает последний сохранённый батч и показывает сводку
  (`ResultsSummary`), легенду статусов (`StatusLegend`) и таблицу
  (`ResultsTable`) с экспортом CSV (`ExportCsvButton`); если батч не запускался
  — пустое состояние. Кнопка «Новый батч» очищает сохранённый батч.
- `StatusLegend` расшифровывает словами статусы карточек, смысл порога
  уверенности и служебных колонок: цвет не является единственным носителем
  смысла (design.md, §8, §11). Раздел свёрнут по умолчанию; раскрывается
  кликом по всей строке заголовка — кнопка занимает ширину шапки и содержит
  текст заголовка и галочку, которая поворачивается по состоянию
  (`aria-expanded`).
- `ConfidenceBadge` для значений ниже порога показывает видимую пометку
  «ниже порога», а не только подсветку.

## Запуск

```bash
npm install
npm run dev        # dev-сервер Vite (http://localhost:5173)
npm run build      # проверка типов и production-сборка
npm run preview    # предпросмотр собранного приложения
npm run typecheck  # только проверка типов
npm test           # unit-тесты (vitest)
```

Базовый URL API задаётся переменной `VITE_API_BASE_URL`. Если она пустая,
запросы идут на текущий origin (`/api/v1/...`) — так работает в docker через
reverse-proxy nginx.
