# Frontend

Веб-приложение SpecFlow на React, TypeScript и Vite. Тексты интерфейса
локализованы через i18next.

## Устройство

- `src/main.tsx` — точка входа (включая `BrowserRouter`).
- `src/App.tsx` — корневой компонент с маршрутами.
- `src/components/` — переиспользуемые компоненты (`AppLayout`, `Header`,
  `FileUpload`, `DataPreview`).
- `src/pages/` — страницы (`PageHome`, `PageResults`).
- `src/hooks/` — кастомные хуки (`useFileParser`).
- `src/lib/` — утилиты (`fileParser` — разбор CSV/JSON/TSV, `inputValidation` —
  валидация обязательных полей, `format` — форматирование значений).
- `src/styles/tokens.css` — токены дизайн-системы (цвета, типографика,
  геометрия).
- `src/index.css` — глобальные стили оболочки и состояний компонентов.
- `src/constants.ts` — константы уровня приложения (в т.ч. параметры
  загрузки файлов).
- `src/i18n.ts` — конфигурация i18next.
- `src/locales/` — переводы (`ru`, `en`).
- `src/schemas/api.ts` — TS-типы, синхронизированные с API-контрактом
  (`openspec/specs/api_contract.md`).
- `src/api/` — клиент API на fetch: единая точка отправки запросов
  (`client.ts`), типизированные методы по эндпоинтам (`index.ts`).
- `public/specflow_logo.svg` — логотип SPECflow (прозрачный фон,
  используется в шапке как есть).
- `vite.config.ts` — конфигурация Vite и dev-сервера.

## Дизайн

Визуальный язык задан дизайн-системой `openspec/specs/design.md`:

- цвета, типографика, радиусы и отступы вынесены в `src/styles/tokens.css`;
  компоненты используют только CSS-переменные;
- палитра монохромная: оттенки серого плюс красный только для ошибок и
  критичных состояний (синий и другие декоративные акценты не используются);
- реализована тёмная тема (основная по спеке); светлая тема и переключатель
  из дизайн-спека пока не подключены;
- в шапке — логотип и название текущего раздела; служебные индикаторы
  (версия пайплайна, статус API) в шапке не показываются;
- фон рабочей области — слабая CSS-сетка, без растровых изображений;
- переходы короткие (`--transition-fast`), при
  `prefers-reduced-motion: reduce` отключаются;
- фокус заметен везде (`:focus-visible`), статусы дублируются текстом.

## Маршруты

- `/` — `PageHome` (главная).
- `/results` — `PageResults` (результаты батча).

Страницы рендерятся внутри `AppLayout` (Header + область контента).
`Header` показывает логотип и название текущего раздела; навигация ведёт на
страницы «Главная» и «Результаты».

## Загрузка карточек

- `FileUpload` — выбор файла (CSV/JSON/TSV) обычным системным диалогом по
  клику; перетаскивание не поддерживается. Отображает состояния ожидания,
  обработки, ошибки и успеха. Компонент не разбирает файл: он принимает статус
  и ошибки снаружи.
- `useFileParser` — разбор выбранного файла: определение формата по расширению,
  чтение, парсинг и валидация минимального набора полей. Возвращает карточки
  (`ProductCardRequest[]`) либо типизированную ошибку (`FileParseError`).
- `lib/fileParser.ts` — чистые функции разбора (без React), покрытые тестами.
- `DataPreview` — предпросмотр первых `PREVIEW_MAX_ROWS` строк: сводка
  валидации обязательных полей (`title`, `description`, `seller_attributes`),
  ключевые поля, обрезка длинных значений с раскрытием, отметка
  незаполненных ячеек; метаданные файла (имя, формат, размер, число
  карточек) показывает `PageHome`.

`PageHome` связывает загрузку и предпросмотр: выбор файла запускает разбор,
кнопка «Убрать файл» сбрасывает состояние. Успешный выбор сам по себе
обработку не запускает.

Формат определяется по расширению; CSV/TSV разбираются через `papaparse`.
Валидация строки: минимум одно непустое из `title`, `description`,
`seller_attributes`; `seller_attributes` в CSV/TSV должен быть корректным JSON.
Разобранные карточки совпадают с типом `ProductCardRequest`
(`src/schemas/api.ts`).

## Запуск

```bash
npm install
npm run dev        # dev-сервер Vite (http://localhost:5173)
npm run build      # проверка типов и production-сборка
npm run preview    # предпросмотр собранного приложения
npm run typecheck  # только проверка типов
npm test           # unit-тесты (vitest)
```

Базовый URL API задаётся переменной `VITE_API_BASE_URL`. Если она пустая,
запросы идут на текущий origin (`/api/v1/...`) — так работает в docker через
reverse-proxy nginx.
