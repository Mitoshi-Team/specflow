## Context

См. `proposal.md` — Why. Текущий пайплайн (`openspec/specs/attribute_extractor.md`) описан как гибридный cheap-first каскад из шести экстракторов с взвешенной агрегацией уверенности (`method_weights`), штрафами (`enum_out_of_vocab`, `conflicting_values`, `weak_evidence`) и LLM как резервом. В коде `services/attribute_extractor` экстракторы реализованы как заглушки (`extract()` возвращает пустой список), реальная логика есть только в `preprocessing.py`, `grounding.py`, `normalization.py` и `registry.py`. Поэтому смена архитектуры затрагивает преимущественно каркас, а не работающую логику.

Разведочный анализ (`EDA/`) показал:

- 49,3% описаний содержат HTML, 41,1% заголовков дублируются; в атрибутах продавца много служебного шума («Подборки», «Продавец», BI-поля, «Гарантия предоставляется», «Потратить бонусы»).
- 10 708 уникальных имён атрибутов при 9 целевых кодах (`brand`, `model`, `color`, `storage`, `diagonal`, `battery_capacity`, `ram`, `drive`, `processor`).
- Доля карточек, где значение атрибута встречается в тексте (заземление по атрибутам продавца): brand 98,2%, model 95,9%, **color 16,8%**.
- Пересечение офферов и карточек (join по `sku_id`) — 241 355 записей.

Из этого следуют два вывода, определяющие дизайн: качество определяется чисткой текста и нормализацией имён полей; для части полей (например, `color`) значения в тексте просто нет, и это ограничение данных, а не алгоритма.

## Goals / Non-Goals

**Goals:**
- Описать пайплайн без LLM: чистка текста → структурированный путь → правила на ядре → NER на хвосте → векторный матч к каталогу → нормализация → rules-fallback.
- Упростить модель уверенности до прозрачной и объяснимой.
- Ввести каталог полей и векторный матч характеристики к каноническому коду.
- Зафиксировать методику получения обучающих данных для NER без полной ручной разметки.

**Non-Goals:**
- Обучение и оценка конкретной NER-модели, её метрики и гиперпараметры (отдельные задачи реализации).
- Изменение публичных путей и формата запросов API (пути `/api/v1/*` сохраняются).
- Изменение кода сервисов в рамках этой правки — только спецификации.
- Выбор конкретной векторной БД и embedding-модели (интерфейс абстрактный).
- UI/фронтенд-логика.

## Decisions

### D1. Чистка текста — обязательный первый этап

Любой входящий текст проходит очистку до извлечения: снятие HTML-тегов, удаление служебных вставок и водяных знаков, мусорных символов, унификация кавычек/тире/пробелов. Обоснование: EDA показал 49,3% описаний с HTML и большой объём служебного шума. В текущей спеке это было «опциональное удаление мусорных символов» — теперь это полноценный этап конвейера.

### D2. NER извлекает две сущности: `CHARACTERISTIC` и `PROPERTY`

Multilingual encoder (token-classification) размечает токены двумя метками:
- `CHARACTERISTIC` — имя характеристики в тексте («корпус», «объём памяти»);
- `PROPERTY` — значение («красный», «256 ГБ»).

Спаны пейрятся в пределах окна (предложение/ближайший контекст). Каждому `PROPERTY`-спану соответствует `ner_score` — вероятность модели. Альтернатива (извлекать готовые пары целиком одной меткой) отклонена: две независимые метки дают больше гибкости при пейринге и переносимости между категориями.

### D3. Структурированный быстрый путь для `seller_attributes`

Поля `seller_attributes` уже структурированы как key→value. Гонять их через NER — терять бесплатную точность. Решение: ключ проходит векторный матч к каталогу полей, значение — нормализацию. Кандидаты получают `extraction_method=structured`. NER применяется только к свободному тексту (`title`, `description`).

### D4. Field resolution через абстрактный `VectorIndex`

Кандидат (ключ из `seller_attributes` или `CHARACTERISTIC` из NER) сопоставляется с каталогом полей `FieldCatalog` через `VectorIndex`:

- `match_score` = близость характеристики к ближайшему полю;
- `match_score >= MATCH_THRESHOLD` → существующий код поля;
- иначе → новое поле (см. D5).

`VectorIndex` — абстрактный интерфейс (`embed`, `add`, `search`); конкретная реализация (FAISS/Qdrant/Chroma/in-memory) не фиксируется. Матч — это **маршрутизация**, а не источник уверенности (см. D8).

### D5. Новые поля: авто-добавление с блоклистом

Если `match_score < MATCH_THRESHOLD`, характеристика проверяется по `FieldBlocklist` (стоп-слова: «Подборки», «Продавец», BI-поля, «Потратить бонусы» и т.п. — выведены из EDA). Если это не шум — поле авто-добавляется в каталог с `is_new_field=true` (код генерируется слагификацией нормализованной характеристики). Мусор отбрасывается. Обязательный блоклист нужен потому, что пространство имён из 10 708 значений содержит много не-атрибутов.

### D6. Нормализация значений

Значение приводится к канонической форме: синонимы (`алый` → `красный`), единицы измерения (`8GB`/`8128 МБ` → `8 ГБ`), регистр брендов/enum, кавычки/тире. Для enum — сопоставление с `vocab`; при исходе вне словаря — `low_confidence` (порядок поведения уточняется в спецификации модуля).

### D7. Rules fallback — только для незакрытых обязательных полей

Детерминированные правила (регулярки единиц + близость ключевых слов) выполняются как fallback: заполняют только те обязательные поля категории, которые не закрыли structured/NER-пути. Кандидаты получают `extraction_method=rule`.

### D8. Упрощённая модель уверенности

- `structured`/`rule` → `DETERMINISTIC_CONFIDENCE` (константа, по умолчанию 0.9).
- `ner` → `ner_score` (softmax модели).
- `match_score` хранится для трассировки и не входит в `confidence` (матч — маршрутизация, иначе авто-добавленное поле парадоксально падало бы в review).
- Пороги: `AUTO_THRESHOLD=0.80`, `REVIEW_THRESHOLD=0.60`; статусы `ok`/`low_confidence`/`partial`, `needs_review`.

Удаляются `method_weights`, формула взвешенной агрегации, штрафы `enum_out_of_vocab`/`conflicting_values`/`weak_evidence`, `hybrid_strategy`, метод `hybrid`. Обоснование: в новой схеме нет смешивания методов, на которое эти механизмы были рассчитаны; TZ ждёт вариативную уверенность (пример 0,98/0,95/0,93/0,81), и `ner_score` её даёт.

### D9. Полный отказ от LLM

LLM исключается из пайплайна, конфигурации, диаграммы архитектуры, API и продуктовых принципов. Обоснование: для 9 целевых полей структурированный путь + правила + NER + векторный матч достаточны; отказ снимает стоимость, латентность и риск галлюцинаций. Ограничение: TZ поощряет сравнение подходов на защите — факт отказа фиксируется как осознанное решение, а не как пробел.

### D10. Доменная модель

`ExtractionMethod = {structured, rule, ner}`. `AttributeCandidate` дополняется полями `ner_score`, `match_score`, `is_new_field`. Вводятся сущности `FieldCatalog`, `VectorIndex`, `FieldBlocklist`, `CharacteristicMatch`, `NewField`. `ConfidenceConfig` = `{threshold_auto, threshold_review, match_threshold, deterministic_confidence}`.

### D11. Персистентность каталога и блоклиста

Авто-добавление новых полей (D5) требует сохранения состояния между запросами: `FieldCatalog` и `FieldBlocklist` персистируются (файл/БД), а не живут только в памяти. Это единственное отступление от «stateless MVP» и должно быть отражено в архитектуре.

## Данные и ML-методология

**Датасет:** `sku_desc.parquet` (sku_id, title, description), `skus.pkl` (офферы с атрибутами продавца), `query_clicks.parquet` (трафик). Отдельного человекоразмеченного gold-набора в датасете нет.

**Обучение NER (distant supervision):**
1. Взять пары key→value из `skus.pkl`.
2. Для карточки (join по `sku_id`) найти значение в `title`/`description`.
3. При совпадении разметить спан как `PROPERTY`, контекст — как `CHARACTERISTIC`.
4. Полученный weak-датасет использовать для обучения NER.

**Малый ручной gold-набор:** несколько сотен карточек, размеченных вручную, — для измерения Precision/Recall/F1 по атрибутам и подбора `MATCH_THRESHOLD`/`AUTO_THRESHOLD`. Без него качество не измеримо.

**Ограничения метода:**
- Слабые метки доступны только там, где значение присутствует в тексте; для `color` это 16,8% → мало обучающих примеров и низкий потолок.
- Ключи атрибутов продавца — это имена полей, а не формулировки в тексте; часть работы по нормализации формулировок берёт на себя векторный каталог.
- Шум атрибутов продавца переносится в метки; малый gold нужен также для контроля этого шума.

## Risks / Trade-offs

- **[Risk] Нет gold-набора.** Невозможно измерить качество и подобрать пороги. → **Mitigation:** зафиксировать создание малого ручного gold в `tasks.md` как обязательный шаг до тюнинга.
- **[Risk] Слабые метки шумные, покрывают не все поля.** → **Mitigation:** ручная коррекция выборки; фиксация потолков (например, `color`).
- **[Risk] Дрейф каталога от авто-добавления полей.** → **Mitigation:** блоклист, периодический аудит новых полей, лимит на число авто-полей.
- **[Risk] Ошибки NER/пейринга вместо галлюцинаций LLM.** → **Mitigation:** grounding как hard-filter, `ner_score`-порог, `source_spans`/`evidence_text`.
- **[Risk] Зависимость от разметки и тяжёлых моделей (encoder + embeddings).** → **Mitigation:** structured/rules пути работают без моделей; NER и векторный матч — подключаемые компоненты с graceful degradation.
- **[Risk] Потолок покрытия по полям, отсутствующим в тексте (`color`).** → **Trade-off:** это ограничение данных; архитектурой не решается, фиксируется честно.
- **[Risk] Рассинхрон `README.md` и фронтенд-типов.** → **Mitigation:** отдельная задача синхронизации.

## Migration Plan

1. Обновить спецификации (эта правка).
2. Синхронизировать `services/contracts`: `ExtractionMethod`, `AttributeCandidate`, схемы API.
3. Переработать `services/attribute_extractor`: `constants.py`/`config.py` (удалить веса/штрафы/LLM, добавить векторные параметры), `merging.py` (упростить), `extractors/` (новый набор, удалить classifier/transformer/llm/dict).
4. Собрать weak-датасет и обучить NER; собрать малый gold.
5. Забустрапить `FieldCatalog` из 10 708 имён + блоклист; подобрать `MATCH_THRESHOLD` на gold.
6. Обновить тесты сервисов под новую модель.
7. Синхронизировать `README.md`, TS-типы фронтенда.

Пункты 2–7 — вне скоупа текущей правки (описываются в `tasks.md` как последующие шаги).
