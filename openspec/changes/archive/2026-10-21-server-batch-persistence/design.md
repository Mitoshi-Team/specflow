# Дизайн: серверная персистентность батчей

## Контекст и ограничения

- Пайплайн извлечения синхронный и уже выполняется в цикле событий FastAPI — блокирующие запросы к БД не ухудшают существующую модель исполнения, а объёмы невелики (один INSERT на батч, один-два SELECT на страницу истории)
- Сбой персистентности не должен прерывать извлечение: карточки уже обработаны
- Юнит-тесты не ходят в реальные внешние сервисы (AGENTS.md); интеграционные тесты с PostgreSQL выделены отдельно

## Решения

### Хранилище: протокол `BatchStore` + две реализации

- `PostgresBatchStore` (psycopg 3, синхронный) — постоянное хранение; включается переменной `EXTRACTOR_DATABASE_URL`
- `InMemoryBatchStore` — режим без настроенного подключения (dev): ограниченная (`IN_MEMORY_BATCH_LIMIT`) очередь в памяти процесса, выбор логируется при старте
- Ошибки драйвера переводятся в `BatchStoreError`; DSN (может содержать пароль) нигде не логируется

### Схема PostgreSQL

Таблица `batches`: `batch_id text PK`, `created_at timestamptz`, `threshold double precision`, `cards jsonb`, `response jsonb` + индекс по `(created_at DESC, batch_id DESC)` для стабильной пагинации. Счётчики списка читаются из JSON-ответа (`response->>'total'` и т.д.), а не дублируются колонками — `response` остаётся источником истины. Схема создаётся идемпотентно при первом обращении (`ensure_schema`): при недоступной БД на старте сервис продолжает работать и повторяет попытку.

Повторный `batch_id` перезаписывает запись (`ON CONFLICT DO UPDATE`): повторный запуск батча с тем же id обновляет историю, дубликатов нет.

### Гарантии при сбое (замечание ревью)

| Ситуация | Поведение |
| --- | --- |
| Запись батча не удалась | Ответ 200 с `persisted=false`, ERROR-лог с traceback; клиент предупреждает о риске потери |
| Чтение истории недоступно | 503 ErrorResponse (`http_error`), ERROR-лог с traceback; не пустой список |
| Неизвестный `batch_id` | 404 ErrorResponse |
| БД недоступна на старте | Сервис стартует, логирует ошибку; схема создаётся при первом успешном обращении (самолечение без рестарта) |

### Контракт

- `BatchExtractResponse.persisted` (по умолчанию `true`) — сервер выставляет явно
- `GET /api/v1/batches?limit&offset` → `BatchListResponse` (`limit` 1–100, по умолчанию 20)
- `GET /api/v1/batches/{batch_id}` → `StoredBatchResponse` (порог, исходные карточки, полный ответ)

### Фронтенд

- `/results?batch_id=...` — батч загружается с сервера; без параметра показывается локальная копия (фолбэк для первой сессии и dev-режима)
- Панель «Предыдущие батчи» на странице результатов: список `GET /batches` (10 последних), переход к любому сохранённому батчу
- Ошибки загрузки видимы (ErrorBanner), а не подавлены; `writeLastBatch` возвращает успех и влияет на навигацию (передача батча через state как последний шанс)
