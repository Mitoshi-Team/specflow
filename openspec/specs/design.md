# `DESIGN.md` — дизайн-система

## 1. Назначение

Этот документ задаёт единый визуальный язык всего продукта Attribute Extractor: интерфейса загрузки, обработки батчей, просмотра результатов, ручной проверки, экспорта и служебных состояний.

Визуальный ориентир — приложенные скриншоты DB SCAN: тёмная рабочая область, компактная верхняя панель, тонкие контуры, сдержанные нейтральные акценты, техническая типографика и аккуратно организованные панели. Переносится именно визуальный язык, а не специфические элементы DBSCAN, его графики, параметры или анимации.

Палитра продукта **монохромная**: интерфейс строится на оттенках серого, а **красный** — единственный хроматический цвет и используется экономно, только для ошибок, отклонённых значений и других действительно критичных состояний. Синий, зелёный, жёлтый и другие декоративные акценты не применяются.

## 2. Принципы

- **Рабочая среда, а не промостраница.** Интерфейс помогает загрузить данные, оценить качество и принять решение по сомнительным результатам.
- **Плотность без перегруженности.** На десктопе можно показывать много строк и атрибутов; содержание разделяется тонкими линиями и ясной типографической иерархией.
- **Данные первичны.** Исходный текст, предсказанное значение, подтверждение, уверенность и метод извлечения должны быть визуально различимы.
- **Состояния объяснимы.** Пользователь понимает, что система нашла, что требует проверки и почему.
- **Цвет не заменяет текст.** Статусы и уверенность обозначаются текстом или значком; красный — только дополнительная подсказка, а не единственный носитель смысла.
- **Сдержанное движение.** Без декоративных анимаций и эффектов при наведении; переходы только там, где помогают отследить изменение состояния.
- **Без растровых декоративных фонов.** Для фона можно использовать CSS-градиенты или очень слабую геометрическую сетку, не мешающую чтению.

## 3. Цветовые токены

Значения ниже — стартовая палитра для реализации. Сохранять её как CSS-токены: не задавать цвета компонентов напрямую, чтобы централизованно поддерживать темы.

Гамма монохромная: различия строятся на светлоте серых поверхностей, границ и текста. Красный присутствует только в семантических токенах `--danger*`.

### Тёмная тема

Тёмная тема — основная и наиболее близкая к референсу.

| Токен | Значение | Применение |
|---|---|---|
| `--bg` | `#101011` | Основной фон приложения |
| `--surface-1` | `#171719` | Панели и основные карточки |
| `--surface-2` | `#1D1D1F` | Вложенные панели, строки таблицы при наведении или выделении |
| `--surface-3` | `#262629` | Поля, контролы, активные области редактора |
| `--border` | `#343437` | Основные тонкие границы |
| `--border-subtle` | `#2A2A2C` | Разделители и малоконтрастные контуры |
| `--text-primary` | `#EBEBEC` | Основной текст |
| `--text-secondary` | `#A3A3A6` | Подписи, вторичная информация |
| `--text-muted` | `#77777C` | Неактивные подписи, метаданные |
| `--highlight` | `#EBEBEC` | Светло-серый акцент: фокус, активные элементы, основная кнопка, ссылки |
| `--highlight-soft` | `#2E2E31` | Подложка активного состояния и бейджей |
| `--text-inverse` | `#101011` | Текст на светло-серых поверхностях (основная кнопка, активный элемент) |
| `--danger` | `#E5484D` | Ошибки, критичные предупреждения, отклонение |
| `--danger-soft` | `#2E1517` | Фон ошибочного или критичного состояния |

Контраст текста и интерактивных элементов должен оставаться достаточным на соответствующей поверхности. Не использовать приглушённый текст для важных значений и действий. Красный не должен становиться фоновым или декоративным цветом интерфейса.

### Светлая тема

Светлая тема использует ту же семантику токенов, но не инверсию цветов «один к одному». Фон должен быть светлым нейтральным, панели — белыми или слегка тонированными, границы — тонкими и серыми, текст — тёмным. Акцент остаётся монохромным (тёмно-серый), красный — семантическим цветом ошибки.

| Токен | Значение |
|---|---|
| `--bg` | `#F4F4F5` |
| `--surface-1` | `#FFFFFF` |
| `--surface-2` | `#FAFAFA` |
| `--surface-3` | `#EFEFF0` |
| `--border` | `#D6D6D9` |
| `--border-subtle` | `#E5E5E7` |
| `--text-primary` | `#171719` |
| `--text-secondary` | `#525257` |
| `--text-muted` | `#7C7C82` |
| `--highlight` | `#2A2A2E` |
| `--highlight-soft` | `#E8E8EA` |
| `--text-inverse` | `#FFFFFF` |
| `--danger` | `#C62A30` |
| `--danger-soft` | `#FAEAEA` |

Поддержать системное предпочтение темы через `prefers-color-scheme` и предоставить явный переключатель темы. Выбор пользователя должен сохраняться между посещениями.

## 4. Типографика

Использовать системный стек без необходимости загружать декоративные веб-шрифты:

```css
font-family:
  Inter,
  ui-sans-serif,
  system-ui,
  -apple-system,
  BlinkMacSystemFont,
  "Segoe UI",
  sans-serif;
```

Для моноширинных фрагментов — исходного текста, JSON, идентификаторов и технических меток:

```css
font-family:
  "SFMono-Regular",
  Consolas,
  "Liberation Mono",
  monospace;
```

Рекомендуемая шкала:

| Роль | Размер | Начертание |
|---|---|---|
| Заголовок страницы | `24–28px` | `600` |
| Заголовок секции или панели | `16–18px` | `600` |
| Основной текст и значения | `14px` | `400–500` |
| Табличный текст | `13–14px` | `400–500` |
| Подписи и метаданные | `12px` | `400` |
| Мелкая техническая метка | `11px` | `500`, только для вторичной информации |

Основной межстрочный интервал — `1.45–1.6`. Не использовать капитель и широко разреженные заглавные буквы для больших объёмов текста. Моноширинный шрифт не должен применяться к основному интерфейсному тексту.

## 5. Сетка и геометрия

- Базовый шаг отступов — `4px`; основные размеры строить на шагах `8px`.
- Радиус мелких контролов — `6px`; карточек и панелей — `8px`; крупных контейнеров — до `10px`.
- Границы — `1px`, тонкие и малоконтрастные. Тяжёлые тени не использовать.
- Максимальная ширина рабочей области — около `1440px`; на больших экранах содержимое выравнивать по центру.
- Внутренние отступы панелей: `16–20px` на десктопе, `12–16px` на узких экранах.
- Между крупными областями интерфейса: `16–24px`.
- Использовать `min-width: 0` в сжимаемых контейнерах, чтобы длинный текст не ломал сетку.

## 6. Основная оболочка приложения

### Верхняя панель

Компактная фиксированная или статичная панель в верхней части экрана:

- Слева — логотип **SPECflow**.
- Рядом или ниже на узком экране — название текущего раздела или батча.
- Справа — навигация по разделам и доступные пользовательские действия.
- Высота ориентировочно `56–64px`.
- Нижняя граница — тонкая; без выраженной тени.

Служебные индикаторы вроде версии пайплайна или статуса API в шапке не размещаются: они отвлекают от навигации и не относятся к рабочему содержимому. Версия пайплайна показывается там, где она относится к данным (например, на странице результатов), как вторичная метка.

Логотип использовать из предоставленного файла. Фон исходника прозрачный: **не подменять прозрачность чёрным прямоугольником и не добавлять чёрную подложку**. Если файл оказался экспортированным с непрозрачным фоном, сохранить исходник как есть и запросить корректный файл с альфа-каналом, а не маскировать фон стилями. Не растягивать логотип; сохранять пропорции и обеспечить достаточный контраст на обеих темах. Не перекрашивать его части без отдельного бренд-токена и подтверждения.

### Навигация

Визуально сдержанная. Предпочтительны несколько текстовых пунктов или компактные вкладки без тяжёлых плашек. Текущий раздел обозначается светло-серым текстом, тонкой линией или мягкой серой подложкой. Не переносить навигацию DB SCAN буквально, если она не соответствует реальным разделам Attribute Extractor.

### Контентная область

Интерфейс должен быть похож на рабочую консоль: ясные панели, небольшой визуальный шум, возможность быстро переходить от общего состояния батча к конкретным карточкам. Основные области продукта:

1. **Загрузка** — выбор файла, поддерживаемые форматы, валидация и предпросмотр.
2. **Обработка** — запуск батча, прогресс, состояние и версия пайплайна.
3. **Результаты** — сводка и таблица карточек/атрибутов.
4. **Проверка** — отбор сомнительных или противоречивых результатов.
5. **Экспорт** — выгрузка проверенных или всех результатов в CSV.

Эти области могут быть реализованы страницами, вкладками или последовательными состояниями SPA. Не добавлять разделы, не подтверждённые продуктовой спецификацией.

## 7. Компоненты

### Кнопки

- Основная кнопка: светло-серая заливка с тёмным (инверсным) текстом, умеренное скругление.
- Вторичная: прозрачная или тонально залитая серая поверхность с тонкой границей.
- Текстовая: без рамки и заливки; только для вторичных действий.
- Деструктивная: использовать красный цвет только для действительно необратимых или опасных действий.
- Высота интерактивной зоны — не менее `40px`; на мобильных желательно `44px`.
- Состояния: обычное, фокус, нажатое, отключённое, загрузка.
- Не делать кнопки ярче всего содержимого страницы без функциональной причины.

### Поля и контролы

- Тёмная/светлая поверхность `--surface-3`, граница `--border`.
- Ясная подпись над полем; placeholder не заменяет подпись.
- Фокус обозначать заметной светло-серой обводкой или внешним кольцом.
- Ошибка сопровождается текстовым объяснением, а не только красной рамкой.
- Для выбора файла показывать ожидаемые форматы и ограничения, если они известны.

### Загрузка файла

Область загрузки — спокойная панель с тонкой границей, короткой инструкцией и обычным системным выбором файла по клику. Перетаскивание файлов не поддерживается: у области нет drag-and-drop поведения. Допустим пунктирный контур, но без ярких градиентов и крупных иллюстраций.

После выбора показывать имя, тип, размер, число распознанных записей и ошибки валидации, если эти данные доступны.

Успешный выбор файла не должен сам по себе запускать обработку. Запуск — отдельное явное действие.

### Предпросмотр

Показывать репрезентативные первые строки и ключевые поля входной карточки. Длинные значения ограничивать по высоте с возможностью раскрытия. Ошибки формата, отсутствующие обязательные поля и пропущенные строки отмечать рядом с соответствующими данными.

### Прогресс и состояние батча

- Показывать статус словами: например, «Ожидает запуска», «Обрабатывается», «Завершён», «Завершён с ошибками».
- Если API предоставляет прогресс — отображать полосу и обработанное/общее число записей.
- Если точный процент неизвестен, не имитировать его: показывать неопределённый индикатор и текстовый статус.
- Не скрывать ошибки и частичный результат после завершения.
- Версию пайплайна отображать как вторичную, но доступную для поиска метку.

### Сводка

Показывать только значения, которые действительно доступны из API, например:

- количество обработанных карточек;
- заполненность атрибутов;
- результаты, требующие проверки;
- ошибки обработки;
- распределение по методам извлечения или уверенности, если данные предоставлены.

Числа и метрики должны иметь понятные подписи. Не кодировать смысл только цветом.

### Таблица результатов

Таблица — основной инструмент для анализа результатов. Рекомендуемые поля при наличии в API:

- карточка / название товара;
- атрибут;
- предсказанное каноническое значение;
- уверенность;
- метод извлечения;
- подтверждающий фрагмент исходного текста;
- статус проверки.

Не уплотнять таблицу за счёт нечитаемого текста. Заголовки колонок ясные и короткие; вторичные подробности допускается показывать в раскрываемой строке или панели деталей. Длинные названия и цитаты переносить или сворачивать с явным действием для раскрытия. Сохранять читаемость таблицы при горизонтальной прокрутке на планшетах и телефонах.

### Детали результата и подтверждение

При выборе строки или атрибута показывать:

- исходную карточку и релевантный фрагмент текста;
- предсказанное нормализованное значение;
- уверенность;
- метод извлечения;
- источник или поле входной карточки, если оно предоставлено backend;
- объяснение статуса проверки, если доступно.

Подтверждающий фрагмент должен быть дословным текстом из входа. Не переформулировать его так, чтобы это выглядело как цитата. Если подтверждение отсутствует, явно показать, что оно не найдено, а не создавать его визуально.

### Экспорт

Кнопка экспорта доступна после появления результатов. Формат CSV обозначать явно. Если пользователь может выбрать область экспорта, варианты должны различать все результаты и результаты, прошедшие проверку. Не показывать действие как успешно выполненное до подтверждения со стороны приложения/API.

### Уведомления и ошибки API

Сообщения размещать рядом с областью, к которой они относятся. Ошибка должна объяснять, что произошло, и по возможности предлагать безопасное следующее действие: исправить файл, повторить запрос или загрузить его снова. Не показывать сырой stack trace в пользовательском интерфейсе. Технические детали допустимы в разворачиваемой диагностике, если backend их предоставляет и они не раскрывают чувствительные данные.

## 8. Уверенность, проверка и семантика цвета

Уверенность показывать числом или процентом только если API возвращает соответствующее значение и его смысл определён контрактом. Не считать, что `confidence` разных методов калиброван одинаково.

Предпочтительный формат:

- числовое значение — видимое рядом с подписью «Уверенность»;
- светло-серая полоса или бейдж — дополнительная подсказка, не единственный носитель информации;
- пороги «высокая / средняя / низкая» — определять по согласованным порогам backend или продуктовой логике, не вводить произвольные пороги в UI.

Состояния:

- **Автоматически принято** — нейтральная серо-светлая маркировка.
- **Требует проверки** — заметная светло-серая маркировка с явным текстом; не красная, чтобы отличаться от ошибок.
- **Ошибка или противоречие** — красная маркировка.
- **Не извлечено** — нейтральное приглушённо-серое состояние.
- **Ручная правка** — отдельная метка, если такой сценарий реализован.

Не использовать красный для обычного низкого процента без контекста, а также для ссылок и основного действия. Низкая уверенность — повод для проверки, не обязательно системная ошибка.

Оттенки серого допускаются в нескольких ступенях (нейтральный, светлый, приглушённый), но они не должны подменять текст: расшифровка состояния всегда присутствует словами.

## 9. Стиль исходного текста и технических данных

Сниппеты исходного текста оформлять компактно, на поверхности `--surface-2` или `--surface-3`. Подтверждаемый фрагмент можно выделять мягкой светло-серой подложкой. Различия между исходным и нормализованным значением показывать явно.

JSON, идентификаторы и технические значения отображать моноширинным шрифтом. Не превращать весь интерфейс в редактор кода: техническая эстетика референса должна оставаться акцентом, а не усложнять работу с каталогом.

## 10. Адаптивность

Брейкпоинты — ориентиры, их можно уточнить по реальной раскладке:

- до `640px` — мобильный экран;
- `641–1024px` — планшет и узкое окно;
- от `1025px` — десктоп.

На мобильных:

- панели переходят в одну колонку;
- таблица превращается в карточки или сохраняет ограниченную горизонтальную прокрутку, если так проще сравнивать атрибуты;
- основные действия остаются доступными без поиска по длинной странице;
- зона загрузки и кнопки удобны для касания;
- модальные окна заменяются полноэкранными панелями, если содержимого много.

На планшетах не сжимать критичные колонки до нечитаемой ширины. На десктопе использовать свободное пространство для параллельного просмотра списка и деталей, если это соответствует структуре приложения.

## 11. Доступность

- Поддерживать клавиатурную навигацию и логичный порядок фокуса.
- Фокус должен быть заметен в обеих темах.
- Интерактивные элементы должны иметь текстовую метку и подходящее доступное имя.
- Не различать статусы исключительно цветом.
- Обеспечить достаточный контраст текста, границ фокуса и важных контролов.
- Статус загрузки, прогресс и ошибки должны быть доступны скринридеру.
- Не использовать слишком мелкий текст для существенной информации.

## 12. Движение и состояния

- Не применять анимации при наведении, масштабирование, подпрыгивание и параллакс.
- Допустимы короткие переходы прозрачности или цвета при смене состояния, ориентировочно `120–180ms`.
- Не анимировать большие блоки данных без функциональной причины.
- При `prefers-reduced-motion: reduce` отключать необязательные переходы и анимации.
- Скелетоны допустимы только как спокойная индикация загрузки; они не должны имитировать результат обработки.

## 13. Не использовать

- Синий, зелёный, жёлтый и другие хроматические акценты: палитра монохромная, единственный хроматический цвет — красный.
- Красный как фоновый, декоративный или основной цвет интерфейса и крупные красные поверхности.
- Функции, графики, параметры и терминологию, относящиеся к DBSCAN, если они не нужны Attribute Extractor.
- Тяжёлые тени, стеклянные поверхности, объёмные градиенты и фотореалистичные изображения.
- Декоративные изображения и фоновые иллюстрации вместо данных.
- Drag-and-drop в зоне загрузки файла.
- Ложный процент прогресса, неподтверждённые метрики и выдуманные подтверждения атрибутов.
- Непрозрачный чёрный фон за логотипом, если исходный файл имеет прозрачность.

## 14. Техническое оформление токенов

Реализовать цветовые и геометрические переменные в общей теме, а не в стилях отдельных компонентов. Пример базовой структуры:

```css
:root {
  color-scheme: dark;

  --bg: #101011;
  --surface-1: #171719;
  --surface-2: #1d1d1f;
  --surface-3: #262629;

  --border: #343437;
  --border-subtle: #2a2a2c;

  --text-primary: #ebebec;
  --text-secondary: #a3a3a6;
  --text-muted: #77777c;
  --text-inverse: #101011;

  --highlight: #ebebec;
  --highlight-soft: #2e2e31;

  --danger: #e5484d;
  --danger-soft: #2e1517;

  --radius-control: 6px;
  --radius-panel: 8px;
  --radius-container: 10px;

  --space-1: 4px;
  --space-2: 8px;
  --space-3: 12px;
  --space-4: 16px;
  --space-5: 20px;
  --space-6: 24px;
}

[data-theme="light"] {
  color-scheme: light;

  --bg: #f4f4f5;
  --surface-1: #ffffff;
  --surface-2: #fafafa;
  --surface-3: #efeff0;
```

Палитру можно корректировать после внедрения логотипа и проверки контраста на реальных экранах, сохраняя зафиксированную семантику токенов.
